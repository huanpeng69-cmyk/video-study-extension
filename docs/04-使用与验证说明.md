# 使用与验证说明

本文件说明如何加载这个扩展、如何使用弹窗里的收听与截图，以及如何验证它符合 [产品设计文档](01-产品设计文档.md) 与 [技术方案](02-技术方案.md)。

**当前版本 0.8.1：类型检查、18 个文件 / 226 项测试与生产构建通过。本次验证了模型正文格式兼容、严格失败处理与诊断展示；0.8.0 的浏览器夹具曾验证逐字显示和关窗续跑。未取得本次用户失败的原始模型返回，未做真实 Key 联调。**

> 当前自动学习行为见 §7.7，JSON 正文格式排障见 §9。§7.1–7.6 保留版本演进记录，不是新版的按钮操作指南。

## 1. 环境与命令

需要 Node.js ≥ 22 与 Chrome/Edge ≥ 116。

```powershell
npm install
npm run compile   # TypeScript 类型检查
npm test          # Vitest 单元测试
npm run build     # 产出 output/chrome-mv3
```

开发热重载：

```powershell
npm run dev        # Chrome
npm run dev:edge   # Edge（需要安装 Edge）
```

## 2. 加载扩展

1. 打开 `chrome://extensions`（Edge 为 `edge://extensions`）。
2. 开启“开发者模式”。
3. “加载已解压的扩展程序” → 选择 `output/chrome-mv3`。
4. 打开任意 B站普通视频页（`https://www.bilibili.com/video/BV...`），**点击工具栏图标**，弹出约 520×600 的弹窗。

> 从旧版升级：在扩展管理页点击“重新加载”，确认版本 0.8.1，然后刷新视频页。不要为升级而卸载扩展，以免删除已有本地资料；重要笔记建议先导出备份。

## 3. 弹窗里的使用方式

### 3.1 收听视频原声

弹窗顶部「收听与画面」区域控制的是**视频本身的音轨**（不是语音合成）：

| 控件 | 作用 |
|---|---|
| ▶ 播放 / ⏸ 暂停 | 播放或暂停视频，声音来自原视频音轨 |
| 时间显示 `当前 / 总长` | 与视频同步，每 1.5 秒刷新 |
| 进度条 | 拖动跳转，视频画面随之跳转 |
| 倍速下拉 | 0.75×–2×，同步到视频元素 |
| 🔊 / 🔇 | 静音与取消静音 |
| 音量滑块 | 0–1，调大会自动取消静音 |

打开弹窗时视频还没开始播放是正常的：在视频页点一下播放，状态就会同步过来（提示“等待播放器状态…”会消失）。

### 3.2 截图视频画面

1. 让视频播放到想要的画面（需要已加载出画面，`readyState ≥ 2`）。
2. 点「截图当前画面」。截取的是**视频帧本身**，不含弹幕、播放器控件和网页其他元素。
3. 缩略图出现后可：
   - 「插入笔记」：以 `![时间](data:image/png;base64,...)` 加一行时间说明写入笔记；
   - 「下载 PNG」：文件名形如 `BV1GJ411x7h7-125s.png`；
   - 「放弃」：清掉这次截图。
4. 受版权保护/加密的视频会让画布被污染，此时会明确提示“截图失败”，不会写入空白图。

### 3.3 字幕、翻译与笔记

获取并载入字幕轨道，或导入 SRT/VTT、从音频转写 → 在设置中确认允许自动发送字幕并授权模型域名 → 继续播放，在「自动学习」页查看 SSE 逐字输出。翻译仍可单独使用，已校验小节可复制到笔记并导出 Markdown；字幕可导出 SRT。

## 6. 本次修复的问题

**现象**：弹窗/侧栏一直停在“播放器尚未就绪”，无法获取字幕。

**原因**（两个叠加）：

1. `bilibili.content.ts` 用裸 `chrome.runtime.sendMessage` 上报上下文，消息没有 `version` 字段；而后台对**所有**消息强制校验 `version !== PROTOCOL_VERSION`，上报被当作“协议版本不匹配”丢弃，后台从未保存视频上下文。
2. 页面元信息只读 `window.aid` / `window.cid`。新版 B站 SPA 下这两个全局变量经常不存在，真正的来源是 `window.__INITIAL_STATE__` 的 `videoData.pages[]`，因此即使消息通过，快照也缺 `cid`。

**修复**：

1. 新增 `postFromContent()`，内容脚本上报统一带信封字段；后台仅在消息**显式声明**版本时才校验。
2. 新增 `src/adapters/bilibili/snapshot.ts`：从 `__INITIAL_STATE__` 取当前分 P 的 `cid`，按 URL 的 `?p=` 匹配 `pages[]`，并与全局变量、URL、DOM 标题、`video.duration` 合并；三路都拿不到 `cid` 时返回 `null`。
3. `CAPTURE_VIDEO` 在缺上下文时主动向内容脚本发一次 `GET_PAGE_CONTEXT`，并等待其上报（最长 2.5 秒），超时给出可操作的错误（不再无限等待）。

### 6.1 第一次尝试（0.2.1，**未能解决**）

当时判断为“启动时序竞争 + 失败无重试”，于是加了有界重试与更宽的超时。
**该判断不完整**：重试只是把同一个确定性失败重复 12 次，界面仍然报错。真正的根因见 6.2。

保留这段记录是为了说明：仅凭“看起来像时序问题”就加重试，而没有把请求/应答链路读到底，会掩盖真实缺陷。

### 6.2 真正的根因修复（0.2.2）：主世界应答被自己的请求吞掉

0.2.1 加重试并没有解决问题，因为失败是**确定性逻辑错误**，不是时序问题。

**证据链**（`bilibili.content.ts` 旧代码）：

```js
// 请求：只带 channel
window.postMessage({ channel, type: 'VSN_READ_STATE' }, window.location.origin);

// 同一个 window 上的应答处理器：只校验 channel
if (data?.channel !== channel) return;
resolve(data.snapshot ?? null);   // 请求里没有 snapshot → 立刻 resolve(null)
```

`window.postMessage` 会把消息派发给同一 window 上的**所有**监听器，**包括刚发出消息的那个上下文**。因此请求一发出，自己的处理器先命中、立刻以 `null` 解析，MAIN 世界桥接的应答永远来不及被接收。

回退路径也无效：隔离世界读不到页面全局变量（实测页面 HTML 只有 `window.__INITIAL_STATE__`，没有 `window.aid = ...`）。

结论：`buildSnapshot()` **每次**都返回 `null` → `emitContext()` 静默返回 → 后台始终读不到上下文 → 恒报“未能读取当前视频信息”。加重试只是把同一个失败重复 12 次。

**修复**：

| 文件 | 改动 |
|---|---|
| `src/adapters/bilibili/bridge-protocol.ts`（新增） | 请求与应答使用**不同类型**（`VSN_READ_STATE_REQUEST` / `VSN_READ_STATE_REPLY`），匹配时同时校验 type + channel |
| `src/entrypoints/bilibili.content.ts` | `requestFromMainWorld()` 只接受 `STATE_REPLY`；改用 `resolveSnapshot()` 保留失败原因；`GET_PAGE_CONTEXT` 回报 `failure`/`diag` |
| `src/entrypoints/player-bridge.content.ts` | 只应答 `STATE_REQUEST`，回 `STATE_REPLY`；加桥接就绪日志 |
| `src/adapters/bilibili/snapshot.ts` | 新增 `resolveSnapshot()`：区分 `unsupported-url` / `main-world-unavailable` / `missing-aid` / `missing-cid` |
| `src/entrypoints/background.ts` | 探针区分「内容脚本未注入」与「快照失败」；`describeSnapshotFailure()` 生成差异化提示；关键节点打日志 |
| `src/lib/log.ts`、`src/lib/guards.ts`（新增） | `[VideoStudy]` 前缀结构化日志；`safeUrl()` 去掉 query 防止泄露令牌 |

**用户提示不再一律相同**：

| 情况 | 提示 |
|---|---|
| 内容脚本未注入/无权限 | 「内容脚本未在此页运行」＋检查网站访问权限、刷新页面 |
| 主世界数据未就绪 | 「页面数据尚未就绪」＋等播放器出现后重新识别 |
| 缺 aid | 「视频页数据缺少 aid」＋反馈视频链接 |
| 缺 cid | 「未能确定当前分 P」＋切到目标分 P 重试 |
| 非视频页 | 「当前页面不是受支持的视频页」 |
| 无 video 元素 | 「尚未检测到可用的播放器信息」＋确认播放器已显示 |

**日志位置**（统一 `[VideoStudy]` 前缀）：

- 视频页控制台：`bridge:ready`、`bridge:reply`、`snapshot:mainWorld`、`snapshot:resolved`、`snapshot:gave-up`
- 扩展 Service Worker 控制台（`chrome://extensions` → 该扩展 → “Service Worker”）：`capture:ok`、`capture:snapshot-failed`、`capture:content-script-missing`、`probe:no-receiver`

日志只记录路径形式的脱敏 URL、布尔字段与计数，不含 Cookie、令牌或媒体地址。

**验证步骤**：

1. `npm run build` → 扩展管理页点“重新加载”（内容脚本必须重载）。
2. 新开 B站普通视频页，等播放器出现，点扩展图标 → 应显示标题、BV 号、第 N P。
3. 视频页控制台应能看到 `[VideoStudy] bridge:reply {statePresent: true, snapshotOk: true}` 与 `snapshot:resolved {ok: true}`。
4. 若仍失败：看日志里的 `failure` 字段定位分支；`main-world-unavailable` 说明桥接未运行（检查是否重载、页面是否为 `/video/` 路径）。

### 6.3 字幕为什么取不到，以及音频转写（0.3.0）

**现象**：视频已能识别（标题、BV、分 P 都对），但点“获取字幕轨道”总是失败，提示“该字幕可能需要登录后读取”或“当前视频未发现可读取的字幕”。

**根因（实测取证，不是推测）**：

1. 直接用 `aid=80433022&cid=137649199` 请求 `https://api.bilibili.com/x/player/wbi/v2`，返回 `HTTP 200, code=0, message=OK`，说明接口本身正常、签名也没问题（补 `wts` 参数结果相同）。
2. 但同一响应的 `data.subtitle.subtitles` 是空数组，且 `data.need_login_subtitle = true`。也就是说：**未登录请求拿不到 `subtitle_url`**。
3. `src/entrypoints/background.ts` 里的 `LIST_TRACKS` 当时写的是 `fetch(..., { credentials: 'omit' })` —— 明确让浏览器**不带** Cookie，于是永远拿到空列表。
4. `parseTrackResponse()` 又会跳过 `subtitle_url` 为空的轨道，`classifyTracks()` 因 `needLogin` 返回 `'login'`，最终变成“需要登录”的提示。

**结论**：字幕接口正常，问题在于扩展主动放弃了登录态。代码从不读取 Cookie 内容，只是让浏览器按站点规则正常附带。

**修复**：`LIST_TRACKS` 改为 `credentials: 'include'`，并新增 `tracks:classified` 日志，记录 `kind` / `count` / `needLogin`，便于区分“确实无字幕”与“需要登录”。

**如何验证字幕能正常获取**：

1. `npm run build`，在扩展管理页点“重新加载”。
2. 在**已登录**的 B站普通视频页打开弹窗，点“获取字幕轨道”。
3. 预期：出现以语言命名的轨道按钮（如“中文（简体）”），点一条即载入字幕，底部显示“已载入 N 条字幕”。
4. 打开该页控制台搜 `[VideoStudy] tracks:classified`：
   - `{kind: 'ok', count: N, needLogin: true}` → 正常，登录态已生效。
   - `{kind: 'login', count: 0, needLogin: true}` → 仍未带登录态：确认已登录、且已授予 `https://api.bilibili.com/*` 权限。
   - `{kind: 'none', count: 0, needLogin: false}` → 该视频真的没有字幕，请用下面的音频转写。
5. 对照实验：B站任意**有 CC 字幕**的视频应能列出轨道；只有“AI 字幕”的视频若未登录则仍为 0 条，这是站方限制而非扩展缺陷。

### 6.4 从视频音频转写为字幕

没有字幕（或不想要站方字幕）时，可以从视频音频直接转出带时间轴的字幕。

**使用前提**：设置页填好 Base URL、API Key，并单独填写**音频转写模型**（如 `whisper-1`）。转写复用同一个服务与 Key，但请求 `POST {Base URL}/audio/transcriptions`。Agnes 网关实测存在该端点：不存在的路径返回 `404 Invalid URL`，该路径返回 `401 Invalid token`，说明路由存在、只是需要有效 Key。

**为什么是“实时”**：浏览器只能通过 `createMediaElementSource` + `MediaRecorder` 实时录到正在播放的音轨，无法离线解码整段视频。所以 **10 分钟视频约需 10 分钟**，期间视频会以 1 倍速真实播放并出声。单次上限 30 分钟，可按区间分批。

**实现要点（`src/asr/`）**：

| 文件 | 职责 |
|---|---|
| `extract.ts` | 主世界录制：接管 `<video>` 音轨、按片段录制、按**真实播放进度**切段；停滞 20 秒报错而不是无限等 |
| `bridge-protocol.ts` | 三层协议：页面内请求/事件类型分离，chrome 侧 `ASR_BEGIN` / `ASR_DRAIN` / `ASR_CANCEL` |
| `relay.ts` | 隔离世界转发器：主世界 `postMessage` **到不了** `chrome.runtime.onMessage`，必须由它中转 |
| `client.ts` | 调用 `/audio/transcriptions`，把段内相对秒数**加上分段偏移**还原成原视频时间 |
| `orchestrator.ts` | 边录边转；鉴权/额度类错误立刻中断，普通失败只计数，不伪造空字幕 |

**避坑记录（两个真实缺陷）**：

1. 旧实现让主世界直接推给后台，但两套通道不互通，后台永远收不到分片。现改为「主世界 → 隔离世界转发器 → 后台拉取」，1.5 秒的拉取间隔也顺带解决 MV3 Service Worker 30 秒空闲被回收的问题。
2. 旧实现在 `finally` 里 `ctx.close()`。`createMediaElementSource` 对同一元素只能调用一次，一旦 close，该 `<video>` 会**永久无声**，用户必须刷新页面。现改为模块级 `WeakMap` 复用同一个 AudioContext，只断开录音分支、绝不 close。
3. 音频转写不是魔法：它受实时录制约束，无法离线解码整段视频。没有音频轨、或音轨受保护的视频会明确报错，不会产出空字幕。

## 7. 后台总结与生成提速（0.4.0）

### 7.1 总结如何触发、包含什么、弹窗关闭后怎么看

**触发**：在 B站视频页打开弹窗 → 载入字幕（站方轨道 / 导入 SRT·VTT / 从音频转写）→ 切到「总结」页点「生成学习总结」。已配好 Base URL 与 API Key 即可。重复点击不会重复提交：检测到同一视频已有未完成任务时，直接续跑并提示「已继续未完成的总结」。

**关键行为**：点下按钮后任务所有权立即转到后台 Service Worker，弹窗只负责发起与展示进度。**可以立刻关闭弹窗**，生成会继续，直到完成并写入本地数据库。

**输出结构**（0.5.0 起，对齐你提供的目标结构示例 `施工项目进度计划管理_学习笔记.docx`）：

```jsonc
{
  "opening": {                    // 开篇：总体定位或核心认知
    "title": "先建立一个核心认知",
    "paragraphs": [{ "text": "……", "sourceCueIds": ["native-1"] }],
    "bullets": []
  },
  "sections": [                   // 其余章节，按视频顺序
    {
      "title": "进度计划概述",     // 只写标题，编号由界面与导出生成
      "paragraphs": [{ "text": "……", "sourceCueIds": ["native-5"] }],
      "bullets": [
        { "text": "施工总进度计划：……", "sourceCueIds": ["native-10"] }
      ]
    }
  ]
}
```

渲染后即示例的形态：**「一、先建立一个核心认知 / 二、进度计划概述 / 三、……」**，每个章节内部可混排**正文段落**与**列表条目**。

与旧结构（固定五字段 `overview`/`chapters`/`keyPoints`/`terms`/`reviewQuestions`）的差别：旧结构只能给章节塞「要点」，无法写出示例中那种成段的叙述；新结构让章节内部同时容纳段落与条目。`PROMPT_VERSION` 已升到 `p2`，旧结构的总结结果不会被复用。

**概览与复习问答去哪了**：新结构不再单列。视频的整体定位由 `opening` 承担；复习问答这类内容如需保留，应作为章节内的条目写入，并且同样需要字幕依据。

**护栏**（未因结构变化而放宽）：

- 每个正文段落与列表条目都必须带 `sourceCueIds`，且只能引用本批可见的 `cueId`；
- 越界引用被剔除并计数；剔除后不足一个引用的块整体丢弃，不允许删掉引用让校验变绿；
- 无标题或无任何有效块的章节被丢弃；全部章节无效时整批失败，不产出空壳总结。

模型只能使用本次输入的字幕内容，禁止联网、禁止推测未说出的内容；时间轴始终取自原字幕，不由模型生成。合并失败时保留已完成段落并标记「仅覆盖部分内容」，不会把半成品伪装成完整结果。

**弹窗关闭后如何查看已生成的结果**（三种入口）：

1. **重新打开弹窗**：自动读取该视频最新总结并显示在「总结」页；若任务仍在跑，底部进度条会接着显示实时进度。
2. **资料库**（弹窗右上「资料库」）：列表每行显示「总结已完成 / 后台整理中 x/y 段 / 无总结」，每 3 秒刷新一次，无需停留在视频页。
3. **导出**：总结页「复制到笔记」，或笔记页导出 Markdown（含总结）。

### 7.2 定位「生成超级慢」的具体环节

先量化，再动手。用真实分块函数跑基准（`$PI_SCRATCH_DIR/bench-summary.ts`），单次模型往返按保守的 12 秒计：

| 场景 | 字幕条数 | 旧段数 | 旧串行耗时 | 新段数 | 新并发耗时 | 加速 |
|---|---|---|---|---|---|---|
| 20 分钟视频 | 480 | 8 | 1.6 分 | 2 | 0.2 分 | 8.0x |
| 60 分钟视频 | 1440 | 24 | 4.8 分 | 6 | 0.4 分 | 12.0x |
| 120 分钟视频 | 2880 | 48 | 9.6 分 | 12 | 0.8 分 | 12.0x |

**根因（按影响排序）**：

1. **分块上限过小，把请求数放大了 4 倍**（主因）。`DEFAULT_MAX_CUES_PER_CHUNK = 60`、`DEFAULT_MAX_CHARS_PER_CHUNK = 3000` 意味着每 60 条字幕就要一次完整的大模型往返。1440 条字幕被切成 24 段——总耗时与段数成正比，而切成 60 条对质量毫无增益。
2. **抽取阶段严格串行**。旧实现是 `for (const plan of pendingPlans)`，第 N 段的请求要等第 N-1 段返回才开始，总耗时 = 段数 × 单段延迟，网络与模型算力大量闲置。
3. **`max_tokens` 固定 2048，与长输入不匹配**。输入变长后输出更易被截断 → 返回的 JSON 非法 → 该段判失败 → 整段重试。用户感知的「慢」里有相当一部分是这种无效往返。

### 7.3 优化方案（总结内容质量不变）

| 措施 | 改动 | 为什么质量不降 |
|---|---|---|
| 放大分块 | `240 条 / 8000 字` | 分块仍以**完整 Cue** 为边界，不切割单条字幕；每段依然带前后文（`contextBefore/After`），合并阶段输入仍是各段的完整结构化摘要 |
| 有界并发 | 固定 3 个 worker 抢任务，而非 `Promise.all` | 并发不改变任何一段的输入与提示词，只改变等待方式；限 3 是为兼容免费层 RPM，避免被限流反而更慢 |
| 自适应输出预算 | `summaryOutputBudget(输入字符数)`，取值 1024–8192 | 只放宽输出长度上限，提示词与校验规则完全不变；减少「截断→重试」这一纯损耗 |
| 失败隔离 | 单段失败不阻塞其他段，已完成的段照常落库 | 与旧行为一致（旧实现也是计数后继续），但并发下不会因一段慢拖住全部 |

**质量护栏未改动**：`validateSummary` 的引用校验、只允许本批 `cueId`、空引用条目不输出、`PROMPT_VERSION` 参与缓存指纹——全部保持原样。

### 7.4 如何验证优化效果

1. **自动化**：`npx vitest run tests/summary-service.test.ts`（9 项）与 `tests/chunking.test.ts`（4 项）。覆盖：分块上限已上调、1440 条字幕不再产生几十段、分块仍以完整 Cue 为边界且 cueId 不重不漏、前后文仍存在、超长单条不被切开、输出预算单调不减且有上下限。
2. **段数对比**：`npx tsx $env:PI_SCRATCH_DIR/bench-summary.ts`，对照上表确认新旧段数与加速比。
3. **真机观察**：
   - 打开弹窗点「生成学习总结」，底部应显示「后台整理中 x/y 段」；`y` 应明显小于旧版本。
   - 视频页控制台搜 `[VideoStudy] summary:start`，`chunks` 字段即本次段数。
   - 关闭弹窗等 1 分钟后重开：进度应已推进（证明后台在跑）；或打开资料库看该行状态。
4. **质量回归**：对同一视频生成总结，确认概览/章节/核心知识点/术语/复习问题齐全、每条带可点击的时间引用、点击能跳到正确位置。优化只动速度参数，结果结构应与优化前一致。

### 7.5 随视频播放逐步产出总结（0.6.0）

**设计决定**（已与用户确认）：仅在**字幕已就绪**时增量生成；按**固定时间间隔**切段；每步输出为**追加**（新章节依次往下长）。

#### 更新粒度与频率

| 项 | 取值 | 理由 |
|---|---|---|
| 切段依据 | **固定时间间隔，默认 5 分钟/段** | 按条数切会让每段覆盖时长忽长忽短，进度条与视频时间对不上；按时间切后段与时间一一对应，可解释 |
| 段内上限 | 仍受 240 条 / 8000 字约束 | 防止极端密集字幕把单段撑爆 |
| 更新频率 | 每**完成一段**立即产出一次（不是每 2 秒） | 以模型返回为节奏，避免空转；实测 30 分钟视频切成 6 段，即最多 6 次刷新 |
| 界面刷新 | 弹窗每 **2 秒** 读一次快照，仅在章节数增长时才更新 | 兼顾响应速度与无谓重渲染 |

切段边界永远是**完整 Cue**，时间轴取自原字幕，不因分段重算。

#### 追加还是替换

**追加**。章节顺序 == 分段顺序 == 视频时间顺序，所以新章节永远接在末尾，用户看到的是「越往下越接近视频后段」，不会出现内容跳动或重排。

| 阶段 | 做什么 | 是否调用模型 |
|---|---|---|
| 生成中 | 把已完成各段的章节**直接拼接**成快照，标 `coverage='partial'` | 否（纯结构拼接） |
| 全部段完成 | 做一次真正的**归并**，压掉跨段重复观点，标 `coverage='complete'` | 是（一次） |

为什么生成中不做模型合并：合并是一次完整的大模型往返，每完成一段就合并一次会让总耗时反而更长。代价是阶段性快照里可能有跨段重复——UI 以「正在生成中」明确标示，并说明「全部完成后会自动合并去重」。

#### 前端如何呈现

| 位置 | 呈现 |
|---|---|
| 总结页 | 章节实时往下长，每条结论仍带可点击时间引用 |
| 顶部提示 | 生成中显示**蓝色「正在生成中」**：*「以下为已产出的部分章节，后台仍在继续；全部完成后会自动合并去重。」* |
| 底部进度条 | `后台整理中 x/y 段（共 N 条字幕）`，合并阶段变为「各段完成，正在合并为完整总结」 |
| 生成结束 | 提示变回常规完成态，内容已是合并后的完整版本 |

弹窗关闭 → 轮询停止，后台继续；重开弹窗会自动补显已产出部分（`else if (!visible && progress.completed > 0)` 分支），不会出现空白。

#### 验证

1. **自动化**：`npx vitest run tests/summary-service.test.ts`（14 项）。新增 3 项覆盖时间切分：每段覆盖时长不超设定间隔、不传 `intervalMs` 时与旧行为完全一致、时间切分后仍以完整 Cue 为边界。
2. **端到端**：`npx tsx $env:PI_SCRATCH_DIR/verify-incremental.ts`，输出 30 分钟 / 600 条字幕 → 6 段，段边界精确落在 0–300s、300–600s…，并打印每次完成一段后快照章节数的递增过程。
3. **真机**：打开视频页 → 生成总结 → 观察章节是否随时间推进逐条出现，而不是等全片结束才一次性出现。

### 7.6 页内悬浮窗已撤销：它把视频页整成白屏（0.7.1）

0.7.0 曾把界面从浏览器级弹窗改成「注入视频页的 Shadow DOM 悬浮窗」，目标只是让**点页面别处不关闭**。该方案已**整体撤销**，原因是它引入了更严重的问题：**B站视频页整页白屏**。现已回到标准弹窗（`default_popup`）。

#### 白屏是怎么造成的

悬浮窗要能显示，就必须让承载 iframe **铺满整个视口**（`inset:0; width:100%; height:100%`）——因为界面挂在 iframe 自己的 document 里，iframe 尺寸为 0 时浮层会被裁进零尺寸视口而不可见（这正是 0.7.0 中途修过的另一个缺陷）。但一个铺满视口、`z-index` 取最大值的 iframe 层，本质上就是**盖在整页之上的东西**：

- 它依赖 `pointer-events:none` 把鼠标「穿透」过去，这是纯 CSS 的补偿，任何一环失效就会挡住整页交互；
- B站页面自己会频繁改动 DOM（播放器初始化、分 P 切换、弹幕层），注入的顶层节点一旦没有被及时清理或误判，就会长期驻留；
- 该层对页面而言是**不可见的外来覆盖物**，出问题时表现为「页面在、内容不渲染/点不动」的白屏。

用一个覆盖整页的层去实现「点别处不关」，代价与收益完全不成比例——为了一个小面板的交互细节，押上了宿主页面能否正常渲染。这是决策失误，不是实现瑕疵。

#### 撤销内容

| 项 | 处理 |
|---|---|
| `src/entrypoints/overlay-inject.content.ts` | 删除（注入全屏 iframe 的内容脚本） |
| `src/entrypoints/overlay/{index.html,main.tsx}` | 删除（悬浮窗载体扩展页） |
| `src/ui/OverlayShell.tsx` | 删除（Shadow DOM 外壳与样式） |
| `src/ui/overlay-state.ts` 与对应测试 | 删除（只服务于悬浮窗开关） |
| `background.ts` 的 `chrome.action.onClicked` | 删除（不再需要后台转发切换） |
| `wxt.config.ts` 的 `action` | 恢复 `default_popup: 'panel.html'`；`overlay.html` 移出 `web_accessible_resources` |

#### 「弹窗关闭但读屏不中断」为什么本来就成立

这一条**不需要悬浮窗**。总结生成任务的所有权在 **Service Worker**（`startSummary` 写入 `ownerId: 'background'`），弹窗只是读取 `SUMMARY_PROGRESS` 的**展示层**：

- 关掉弹窗 → 展示层消失，但任务仍在后台跑；
- MV3 的 Service Worker 会被浏览器回收，因此由 `chrome.alarms` 的 `summary-heartbeat`（每分钟）以及 `onStartup`/`onInstalled` 唤醒它继续推进；
- 每完成一段就落库一次快照，所以即使中途被回收，恢复后从已完成段继续，不必从头再来；
- 重开弹窗会自动补显已产出的部分（`useStudyWorkflow` 轮询 + `coverage='partial'` 快照），不会出现空白。

#### 验证

1. **构建产物核对**：`npx wxt build` 后确认 `output/chrome-mv3/` 中 `overlay.html` 与 `content-scripts/overlay-inject.js` **均已不存在**；`manifest.action` 为 `default_popup: 'panel.html'` + `default_title`；`web_accessible_resources` 仅剩 `library.html`、`options.html`；背景脚本中 `TOGGLE_OVERLAY` 与 `onClicked` **均已消失**，而 `summary-heartbeat` / `START_SUMMARY` / `ownerId` 仍在。
2. **自动化**：`npx tsc --noEmit` 与 `npx vitest run` 全通过（12 文件 / 98 项）。
3. **真机**：打开 B站视频页应正常渲染、无白屏；点工具栏图标弹出**标准弹窗**；生成总结后关闭弹窗等待，再从资料库或重开弹窗确认内容仍在继续增长。

### 7.7 SSE 流式 + 30 秒自动触发（0.8.0，当前行为）

**不再点「生成学习总结」**。保留标准弹窗、旧总结、资料库、笔记和导出；执行方式改为真实播放进度驱动的后台 SSE，弹窗仅显示结果与控制自动学习开关。没有页内浮层、iframe 或新增权限。

#### 使用步骤

1. 重新加载 `output/chrome-mv3`，确认版本 0.8.0，**刷新视频页**以更新内容脚本。
2. 在设置中填写当前服务的 Base URL、支持 Chat Completions SSE 的对话模型与 Key，并授权模型域名。
3. 勾选「允许按播放进度自动发送当前字幕片段到上述服务」，保存设置。未确认、缺少 Key 或未授权域名时，不会自动发起模型请求。
4. 获取并载入字幕轨道，或导入 SRT/VTT、从音频转写。自动学习基于已保存字幕，不会自动抓屏或自动开始录音。
5. 继续播放，打开「自动学习」页观看正文逐字出现。**弹窗可以关闭，后台仍继续**；重开会同步当前草稿与已保存小节。

#### 触发与结果规则

| 情况 | 行为 |
|---|---|
| 播放 0–29.999 秒 | 不提前读取 0–30 秒的未来内容 |
| 到达 30 秒、60 秒 | 分别触发节点 0（0–30 秒）、节点 1（30–60 秒） |
| 自然播放结束 | 补齐不足 30 秒的尾段；短于 30 秒的视频也可处理 |
| 暂停视频 | 不创建或启动新节点；已在途的 SSE 可完成 |
| 向前拖动 | 只处理最新到达的完整区间，不一次性补跑大量跳过内容 |
| 回退或重复上报 | 水位与稳定节点主键去重，不重发已完成节点 |
| 切换分 P / 字幕版本 | 按视频和字幕版本隔离；旧文档进度与迟到结果不能混入新版本 |
| 无可用字幕的节点 | 标为无字幕，不请求模型，不编造结论 |
| 暂停自动学习 | 明确取消当前请求并阻止后续自动触发；已有成稿保留 |
| 重试失败段 | 只补失败或未完成节点，已完成节点不重发；未知的服务端处理可能已经计费 |

每节点输出独立章节，标注原视频时间范围。只有完整接收且所有正文引用均来自本节点 cueId 时，才写入原 `summaries` 表；不再调用整片合并去重。小节按时间排序，失败段补齐时回到对应时间位置，不重写已完成小节正文。流式草稿明确标注「引用尚未校验」，不进入复制到笔记、Markdown 或 JSON 备份。

#### 后台续跑与失败处理

- `PLAYBACK_POSITION` → `autoSummaryService.observe()` → 持久化节点 → `streamChat()` → 引用校验 → 原子提交节点与聚合结果。
- 弹窗通过可信 `runtime.Port` 订阅正文预览；关闭时仅退订，不取消 SSE。初次打开/重连读快照，每 2 秒有只读同步兜底。
- 数据库 v2 只增 `autoSummarySessions`、`summaryNodes`，保留原数据；旧未完成批量总结任务暂停，不与自动节点同时请求。备份格式仍兼容 v1，只包含已校验结果，不包含运行队列、草稿与 Key。
- 每视频一个在途流、全局最多两个、单视频最多积压 8 个排队节点；连续三个节点失败停止自动请求。鉴权、额度或授权类错误立即阻止后续请求。
- 请求总超时最多 180 秒；请求期间才维持 Worker 活动。Worker 意外终止会断开原连接，心跳可有限恢复未完成节点（自动重试最多一次），不是无限重连，也不能保证断网时零重复计费。

## 9. 模型正文不是合法 JSON（0.8.1）

### 报错层级与已复现的缺陷

`模型返回的不是合法 JSON` 来自模型**正文**的二次解析，不是 SSE `data:` 帧的外层 JSON 解码。在自动学习中，该步骤位于完整流接收之后。收到 `[DONE]` 只能证明流结束，不能证明模型遵守了结构化输出格式。

旧 `extractJsonText()` 从首个 `{`/`[` 截至最后一个对应右括号，未检查嵌套层级和字符串。用测试夹具确认：合法 JSON 前有 `[说明]`，或后有 `附注：{仅供核对}` 时，旧代码均抛出了相同报错。修复前这两个定向测试失败，修复后通过。这证明了解析器缺陷，**不等于已确认用户此次原始返回一定属于这两种情况**。

### 修复边界

- 按层级、字符串及转义扫描独立根结构，不再贪婪拼接前后包装文字；未完成根对象不能用内部子对象替代。
- 只做不改变值的兼容：真正的尾逗号移除、字符串内原始控制字符等价转义、完整 JSON 字符串解包一层。正文里的括号、引号、反斜杠和引用 ID 保持原值。
- 开头显式标记的思考区不参与正文解析或流式正文预览，正文字符串中的标签字样不删除。
- 纯文本、未闭合结构、缺失值、歧义引号或多份 JSON 结果仍失败；不会靠补造括号、字段或 cueId 强行入库。
- 引用校验完全保留。解析成功但引用越界仍为 `VALIDATION_FAILED`，不放入成稿、笔记或导出。
- 仅加强提示词的 JSON 语法要求，不添加未经确认的接口参数，不增加网络重试次数，不重置已完成节点或旧笔记。

## 10. 多站点通用化与 YouTube 字幕（0.9.0 → 0.9.1）

### 10.1 为什么必须通用化

原实现把「读字幕」绑死在 B站接口上：平台、网络环境或账号任意一项不满足，整个学习流程就不可用。0.9.0 起改为「B站降级为可选适配器，底座只用浏览器标准能力」，保证缺失适配器时功能降级而不是整体失效。

### 10.2 磁盘上真实存在的缺陷（0.9.1 修复）

**缺陷：YouTube 字幕能列出轨道，却解析出 0 条。**

证据链：`parseYouTubeCaptionTracks` 能从 `ytInitialPlayerResponse` 正确取到 `baseUrl`，说明探针与轨道枚举都是通的；但 `baseUrl` 在不带 `fmt` 参数时返回的是 **XML timedtext**：

```xml
<transcript><text start="0.5" dur="1.2">你好</text></transcript>
<!-- 或 srv3： -->
<timedtext format="3"><body><p t="500" d="1200"><s>你好</s></p></body></timedtext>
```

而下游唯一入口是 `parseSubtitleText(text, 'vtt')`，它只认 SRT/WebVTT 的 `-->` 时间行。于是每条 `<text>` 都被判为「无法识别时间行」，全部计入 rejected，最终抛 `PARSE_FAILED`。表现就是「明明有字幕，却一条也读不到」。

**修复**：新增纯函数模块 `src/domain/timedtext.ts`，提供 `parseTimedText`（v1/v2 与 srv3 两种 XML 形态）与 `parseJson3Captions`（JSON3 的 `events[].segs[].utf8`）；`page-video.ts` 的两个取回出口（本世界 `fetch` 与主世界探针）统一经 `toVttText` 归一后再交给既有校验。同时探针请求时显式带上 `fmt=json3`，减少一层容错负担。

时间轴只搬运源数据里真实存在的值：条目缺 `dur` 时用**下一条的真实起点**收尾；最后一条仍无法推导时长则丢弃并计入 rejected，由界面如实提示，绝不猜测补造。

### 10.3 其他已修复的通用性问题

## 11. 校验失败排查与本地语音转写（0.10.0）

### 11.1 三类「生成结果未通过校验」的真实来源

用真实校验器（不 mock）复现后，结论如下：

| 用户看到的提示 | 触发条件 | 性质 |
|---|---|---|
| 节点存在空正文 | `text` 缺失、为空白、或为非字符串 | 模型确实没写正文 |
| 节点条目格式无效 | 条目是 `null`/数字/数组，或 `text` 是含额外字段的对象 | 结构不可保值还原 |
| 节点条目过多（超过 24 条） | `paragraphs` + `bullets` 合计超 24 块 | 既有上限 |

**关键发现**：单条 9000 字的长正文**本来就能通过**——它会被无损切成两块并各自保留原引用。所以「正文超出长度限制」并非 `MAX_TEXT=8000` 直接拒绝，而是两种情况之一：

1. 模型输出被 `finish_reason=length` 截断（提示为「模型输出因长度限制被截断」）；
2. 条目过多触顶（合计超过 24 块）。

### 11.2 修复内容（不放宽任何上限、不补造内容）

**补充（0.10.1，针对 `phase=model-json; kind=syntax`）**：用真实解析器复现后确认，中文模型最常见的 `syntax` 成因是**把结构位的 `,` `:` 写成全角 `，` `：`**。此前 `normalizeSyntax` 只处理尾逗号与字符串内控制符，因此这类正文被判定为语法错误。现已加入**字符串外**的全角标点等价替换：

- 只在引号之外替换 `，`→`,`、`：`→`:`，**字符串内部一字不改**（正文里的「第一点，第二点：结论」原样保留）；
- 单引号、缺值（`{"a":,}`）、缺括号、全角花括号 `｛｝` 仍**明确失败**，不猜测修补；
- 修复后仍走原严格引用校验，不因格式兼容放过越界引用；
- 兼容日志新增 `widePunctuation` 计数，便于区分是哪类偏差。

1. **已知包装解包**：`{section:…}` / `{summary:…}` / `{result:…}` / `{data:…}` 与「只有一个元素的根数组」可保值解包；多个候选键或超过 4 层仍明确报 `wrapper-ambiguous` / `wrapper-depth`。
2. **单层 `text` 对象还原**：`{"text":{"text":"正文"}}` 还原为字符串；含额外字段、内外引用不一致则报 `text-type`。
3. **引用校验更严格**：不再用 `filter` 丢掉非字符串元素后假装合法；空白、越界、非字符串直接报 `refs-type` / `refs-format` / `unknown-refs`。
4. **超长正文无损切分**：优先句末，若因此超出 24 块预算则改用码点硬切；两种都超预算才失败。切分不会落在代理对中间，也不会产生空白分片。
5. **块数预算按两侧共享**：先算另一侧最少占用，再给本侧留预算，避免「各自合法、合计超限」。
6. **提示词显式给出上限**：标题 ≤200、单块 ≤8000、合计 ≤24、字段必须是数组、`sourceCueIds` 非空等。
7. **诊断可区分**：失败一律带 `kind=…`，界面可据此判断是「模型没写正文」还是「结构不可还原」。

### 11.3 本地语音转写（替代云端 ASR）

原实现用网页 `MediaElementSource` 接管 `<video>` 音频上传到云端 `/audio/transcriptions`，会在跨域媒体上失败并使站点静音，还必须依赖聊天 Key。现改为：

1. `tabCapture.getMediaStreamId` 取当前标签页音频；
2. 扩展**离屏文档**（`offscreen.html`）建流采集，每 30 秒成一个独立可解码 WebM 分片；
3. 逐片 POST 到本机 `http://127.0.0.1:8765/v1/audio/transcriptions`；
4. 分片时间戳 + 片段偏移还原为原视频时间，结束时保存一个字幕版本。

停止条件（避免错误时间轴）：暂停、跳转（偏差 >1.8 秒）、静音、音量 0、非 1 倍速、进度停滞 >6 秒、队列积压、单次超 2 小时。

### 12.1 边看边读字幕

**它的做法**

- 列表用 `aria-current` / `data-subtitle-active` 标记当前句，而不是整段重渲染。

**我方原状（差距）**

- `TranscriptPanel.tsx` 只有「搜索 + 单击选择 + 双击跳转」，**完全没有播放位置概念**：不知道当前播到哪一句，也不会跟随或高亮。

**已做改进**

- 新增纯函数 `src/ui/followCue.ts`：`activeCueAt`（含重叠取最新规则）、`cueAtCapture`（截图用，见下一节）、`cueExcerpt`（摘录半径）。
- `TranscriptPanel` 新增可选 `positionMs` prop，缺省时行为与旧版完全一致（向后兼容）：当前句高亮 `.cue.active`、`aria-current`、状态栏显示「当前 mm:ss」、自动 `scrollIntoView({block:'nearest'})`。

### 12.2 截帧做笔记

**它的做法**

- `useFrameCapture.ts`：截屏后**顺手把画面对应的字幕一起存**。`cueAt` 特意允许「刚结束 ≤4 秒」的那一句，注释写明「截图通常发生在让人想保存的那句话之后」。取不到字幕就只存图，不报错。
- `subtitleExcerpt.ts`：摘录默认向前后各扩 1～2 条（用户可选 0/1/2），**按 `track.cues` 原始下标切片**（搜索/分页不影响），超 2000 字明确报错。
- `captureFrame.ts`：同一套逻辑覆盖同源 canvas 读取与**跨域 iframe 的屏幕捕获**两条路径，并给出可操作错误文案（「这个来源的视频不允许读取画面。下载到本机后即可截屏。」）。

**我方原状（差距）**

- 截图只写入时间戳：`![mm:ss](dataUrl)` + `> 截图于 mm:ss`，**不带任何字幕原文**，用户要再回字幕页手动选一遍。
- 截图走 `canvas.toDataURL('image/png')`，跨域媒体污染时失败；错误文案笼统。

**已做改进**

- `insertFrame` 改用 `cueAtCapture`：当前句优先，否则取刚结束 4 秒内的那句，自动附上原文与译文（若已翻译）。**取不到就只写时间戳，绝不编造字幕**。
- 字幕面板显式提示「截图会附上 [mm:ss] 这一句的字幕」，让用户预期一致。
- 新增「上下文 ±0/±1/±2 条」选择，加入笔记时按原文顺序扩展。

**未采纳**：它的 `getDisplayMedia` 屏幕捕获兜底（用于跨域 iframe 取像素）。我方是浏览器扩展，**已有更有权能且不需用户每次授权的路径**——`chrome.tabs.captureVisibleTab`；但该能力需要 `activeTab`/`tabs` 之外的新权限，本轮**未擅自新增**，故跨域媒体（如 YouTube `googlevideo.com`）截图仍会明确失败。

### 12.3 一键转录

**它的做法**

- `internal/transcription/jobs.go`：任务状态机 `resolving → fetching → saving → completed/failed/canceled`，**同一时刻只允许一个 active 任务**（`ErrBusy`）；同一内容同一 preview 复用已有任务而不重复起。
- `Preview` 模式只转**前 60 秒**（`limit = 60`），用于让用户先确认音轨可用再整片转写。
- 起任务前先**读一次现有字幕版本号（revision）**，保存时以该 revision 做校验；若期间别处改过字幕，返回 `subtitle_conflict` 而**不覆盖**。
- 失败按阶段给出不同 code：`source_unavailable` / `audio_timeout` / `invalid_transcript` / `tools_not_ready` / `subtitle_conflict`，而不是一句「转写失败」。

**我方原状（差距）**

- 本地转写**没有 preview 试转**：用户必须整段播放实时采集，才第一次知道音轨/模型是否可用。
- 有「同一时间只允许一个会话」和 `asrSeen` 分片去重，但**没有「保存前 revision 校验」**，理论上并发修改会被覆盖。
- 失败码已区分（`LOCAL_WHISPER_UNAVAILABLE` / `LOCAL_WHISPER_ERROR` / `CAPTURE_UNAVAILABLE` / `NO_SPEECH`），但**没有按阶段细分**（是取音轨失败、还是模型失败）。

**已做改进（本轮）**：无代码改动，仅记录差距。原因如下——

「preview 试转 60 秒」在我方架构下等价于**先录 60 秒再提交**，仍要用户实时等待；它之所以能秒出，是因为后端可以直接按时间轴切远端音频，而我是**标签页实时采集**，没有可跳转的音轨源。强行实现会变成「假装是预览」的假功能，故不做。

revision 冲突校验与阶段化失败码属于值得做但**会改动转写持久化契约**的改动，按「不破坏现有结构」的要求，留作后续单独评估。

## 14. 采集卡在 0/1、退出后进度丢失（0.12.1）

### 14.1 阻塞点：跨文档消息类型写着不一致（确定性 bug）

**现象**：点「从音频转写」后进度一直 `0/1`，永远不出字。

**定位**：进度条的两个数字来自后台的会话状态——

```ts
completed: view.completedChunks,
total: Math.max(view.completedChunks + view.queuedChunks, 1),
```

`0/1` 说明 `completedChunks` 与 `queuedChunks` **都是 0**，即后台从未收到任何分片事件。

**根因**（`background.ts` 与 `offscreen/main.ts` 各写了一份字面量，且不一致）：

| 位置 | 发出的类型 | 判断的类型 |
|---|---|---|
| 离屏文档 | `type: 'event'` | — |
| 后台 | — | `message.type === 'ASR_EVENT'` |

两者不相等 → 后台的 `handleAsrEvent` **从来没被调用过**。录音其实在进行，分片也在转写，但所有事件都被静默丢弃：进度不动、字幕不入库。因为两边都"看起来正常"，失败没有任何报错。

**修复**：在 `src/asr/tab-protocol.ts` 定义唯一常量 `ASR_BACKGROUND_TARGET` / `ASR_EVENT_TYPE`，离屏文档与后台都引用它，不再各写裸字符串。

### 14.2 顺带修掉的第二个卡点：录音基线用旧快照会被误判为「跳转」

`TabAudioRecorder.start()` 原先直接拿 `input.sample`（后台启动时读到的播放位置快照）作为连续性基线。如果这个快照是几秒前的，第一个真实采样到达时 `captureDiscontinuity` 会算出差值过大 → 判定"检测到跳转" → **一开录就停**。

**修复**：新增 `hasBaseline`，第一条真实采样直接作为基线（不做连续性判断）；`waitForBaseline()` 最多等 5 秒，等不到才退回旧快照开路，避免用户点了没反应。

### 14.3 进度丢失：会话只在内存里

**根因**：`localAsr` 与 `asrSegments` 是 `background.ts` 的模块级变量。Service Worker 被回收（关浏览器、扩展重载、空闲休眠）后整个模块重新求值，两者归零；而字幕只在 `done` 那一刻才 `saveTranscript` 落库。于是：

- 中途退出 → 界面回到"没有任务"，已转写的字全没；
- 因为从未落库，重新开始只能从头再来。

**修复**：

1. 每个 `progress` / `chunk` / 终态都调 `persistAsr()`，把 `{state, segments, seen}` 写进 `chrome.storage.session`。
2. 启动时与首次查询 `ASR_STATE` 时调 `restoreAsr()` 读回。
3. 恢复出来的 `recording/transcribing` **不伪装成仍在录音**（离屏录音已随 SW 一起结束）：有已完成分片就标 `completed` 并立即落成一个字幕版本（标注"中断恢复"）；一片都没有则标 `failed` 并说明原因。
4. `seen` 分片序号一并持久化，避免恢复后重复累加。

**边界**：`storage.session` 在浏览器进程结束后清空，所以**关浏览器仍会丢**——这是刻意的，避免把上次的录音会话长期挂在下次启动里。已完成并落库的字幕不受影响（在 IndexedDB 里）。

## 15. 插耳机被报成「未识别到语音 / 页面静音」的排查与修复（0.12.2）

### 15.1 现象

只是插上耳机，没有对页面做任何静音操作，转写结束时却显示：

```
未识别到语音
没有识别到可用的语音内容 · 请确认标签页音频可听见说话声，且播放未暂停或静音。
确认标签页有可听见的说话声，并停止其他同时发声的播放器
```

这三行分别来自 `describeError()` 的 `title` / `action` 与后台写入的 `message` / `detail`，即错误码 `NO_SPEECH`。

### 15.2 当前是怎么判断「音频输出」和「静音状态」的

1. **音频输出**：扩展从不查询、也不控制系统输出设备。`tabCapture` 会把标签页的原生播放输出掐掉，所以离屏文档里必须自己回放：`source → analyser → AudioContext.destination`。没有 `enumerateDevices`、没有 `setSinkId`，**当时也没有监听 `devicechange`** —— 插拔耳机对扩展是完全不可见的。
2. **静音状态**：唯一来源是页面播放器本身。`page-video.ts` / `bilibili.content.ts` 在 `timeupdate` 与 `volumechange` 时上报 `muted: video.muted`、`volume: video.volume`，经 `PLAYBACK_POSITION` → `TAB_STATES` → `pushSample()` 送进离屏文档，由 `captureDiscontinuity()` 判定。
3. **失败归因**：`done` 事件到达时只要 `segments.length === 0`，后台就无条件写 `NO_SPEECH`，并把录音器收集到的 `warnings` 只留在状态里。

### 15.3 根因（三层，均可逐行核对）

| 层 | 位置 | 问题 |
| --- | --- | --- |
| 判定 | `tab-protocol.ts` `captureDiscontinuity()` | `if (next.muted \|\| next.volume <= 0) return '播放器已静音…'` —— 把「音量 0」与「真实静音操作」混为一谈，且**任何一次采样**即可命中 |
| 处置 | `tab-recorder.ts` `updateSample()` | 命中后统一 `stop(true, …)`：`discard = true` 把**已经录到的 30 秒真实语音一起丢掉** |
| 归因 | `background.ts` `handleAsrEvent()` | 0 条分段 → 无条件 `NO_SPEECH`，文案还写着「请确认…未暂停或静音」，把设备问题说成用户静音了页面 |

叠加结果：插耳机 → Chrome 因输出设备变化重建标签页音频输出 → 采集到的是**数字静音**（音轨可能仍在，`MediaRecorder` 照常出片）→ Whisper 返回 0 段 → 界面显示「未识别到语音 · 请确认没有静音」。用户看到的措辞确实像"扩展认为页面被静音了"，但代码里从未读取过任何设备/静音开关状态。

顺带修掉的两个同源隐患：

- `waitForBaseline()` 5 秒兜底会把 `hasBaseline` 置真，之后第一条真实采样被拿去和**旧快照**比，差值过大 → 误判「检测到跳转」→ 一开录就停。
- `track.onended` 原先 `stop(true, …)`，浏览器结束音轨时把有效分片丢掉。

### 15.4 修复（0.12.2）

1. **静音只认真实静音操作**：新增 `isPlayerMuted(sample) => sample.muted === true`；`captureDiscontinuity` 改为返回结构化的 `captureIssue()`，`muted` / `silent-volume` / `paused` / `rate` / `seek` 分开。
2. **音量 0 不再叫「静音」**：只提示「播放器音量为 0，当前采集不到声音」，`stop=false`、`discard=false`，音量恢复后自动续上；连续 60 秒仍为 0 才停止（仍不丢分片）。
3. **静音需连续确认**：`ASR_MUTE_CONFIRM_SAMPLES = 2`，单次读取抖动不再结束整场录音。
4. **停止时保留已录音频**：静音、暂停、音轨结束都是 `discard=false`；只有时间轴不可信（跳转、倍速、位置非法）才丢弃当前分片。
5. **设备切换只记录事实**：离屏文档监听 `navigator.mediaDevices.devicechange`，记一条警告（"这不是页面静音"）与证据，**不判定静音、不停止录音**；`AudioContext` 被挂起时自动 `resume()`，避免用户突然听不到声音。
6. **采集证据**：新增 `AnalyserNode` 峰值采样（200ms 一次），逐片记录是否低于 `ASR_SILENCE_PEAK = 0.002`；`done` 事件带上 `evidence { chunks, silentChunks, deviceChanged, trackEnded, peak, contextRunning }`。
7. **按证据归因**：`describeNoSpeech(evidence)` 取代无条件 `NO_SPEECH`：
   - 全是数字静音 → `CAPTURE_SILENT`（「采集到的音频是静音」，并明确"页面未静音"；有设备变化时直接点名耳机）；
   - 有声音但采集被中断 → `CAPTURE_INTERRUPTED`；
   - 一片音频都没提交 → `CAPTURE_UNAVAILABLE`；

### 15.6 第二轮：一个分片都没产出（`chunks = 0`）的确定性根因（0.12.3）

现象：视频一直正常播放，仍提示「没有采集到可转写的音频片段」。证据是 `chunks = 0` —— 整场采集**一个分片都没进转写**。

**根因（时序，可逐行核对）**：

1. `background.ts` 的 `pushSample()` 只允许 `localAsr.status === 'recording'` 时转发播放位置；而 `localAsr` 要等 `await chrome.runtime.sendMessage({ type: 'start' })` 返回后才置为 `recording`。
2. 离屏文档的 `start()` 在 `sendResponse({ ok: true })` **之前**执行 `await this.waitForBaseline()`，最长 5 秒。
3. 于是形成死窗口：录音器等采样 → 后台等 start 返回才发采样 → 5 秒后录音器只能退回「旧快照」基线开录。
4. 旧 watchdog 是 `6 秒没有推进就 stop(true, …)`，而它计时起点正好是这 5 秒兜底时刻。留给「第一条真实采样」的余量只有约 1 秒；一旦页面晚一拍（弹窗轮询、后台繁忙、timeupdate 节流），watchdog 立即命中。
5. `stop(true)` 的 `discard = true` 把刚录到的整段音频一起丢掉 → `chunks = 0` → 0 条字幕。

也就是说：**这不是音频采集坏了，而是扩展自己在开录后 6 秒把自己判成了「没在播放」，并把已经录到的音频丢弃了。** 与静音、耳机、设备都无关。

**修复**：

1. `pushSample()` 允许 `starting | recording` —— 采集一启动就送出真实播放位置，基线在约 1 秒内到位，死窗口消失。
2. watchdog 阈值 `6s → ASR_STALL_LIMIT_MS = 15s`（放行缓冲与短暂卡顿）。
3. watchdog 改为 `stop(false, …)`：保留已录分片，判错一次不再让用户白等。
4. 新增结构化停止原因 `CaptureStopKind`（`stall / mute / volume / pause / timeline / track-ended / queue-full / failed / requested / limit / closed / ended`）与 `stopReason`，`describeNoSpeech()` 直接使用录音器记录的原因与对应建议，不再猜。
5. 新增 `emptyParts`：只有「完成但没有一个音频字节」才是 `CAPTURE_UNAVAILABLE`；其余零分片情况一律 `CAPTURE_INTERRUPTED` 并给出真实原因。
6. 停止原因能解释「没出声」（stall/pause/mute/volume）时优先用它，避免把「视频没在播」误报成「音频是数字静音」。
7. 离屏文档的 `stop` / `pagehide` 也带上原因（`requested` / `closed`），且不再丢弃分片。

### 15.7 第三轮：「播放位置没有推进」误停正常播放的视频（0.12.4）

**现象**：视频一直在正常播放，仍提示「播放位置超过 15 秒没有推进，采集已停止」。

**为什么这是误判**：旧 watchdog 的判据只有一条 —— `now - lastProgressAt > 15s`。而 `lastProgressAt` 表示的是「离屏文档收到了一条位置比上次更靠前的采样消息」，这条链路是：

```
页面 timeupdate → content script → SW PLAYBACK_POSITION → TAB_STATES → pushSample() → 离屏 updateSample()
```

链路上任何一处断开，位置就「冻住」，但**标签页音频仍在正常采集**。旧逻辑把「我没收到位置上报」当成了「视频没在播放」——这是拿一个观测不到的结论当判据。会断的地方至少有三处：

1. SW 被回收/重载 → `localAsr` 归零 → `pushSample()` 直接 return；
2. `pushSample()` 有状态门槛（曾经只允许 `recording`）；
3. `updateSample()` 内部有 early return（上一轮新增的 `silent-volume` 分支就是其中之一：音量读到 0 时它每次都在刷新 `lastProgressAt` 之前返回）。

**修复（判据换成可观测的证据）**：

1. 新增 `lastAudibleAt`：由 `AnalyserNode` 每 200ms 实测峰值决定，测到 ≥ `ASR_SILENCE_PEAK` 就刷新。这是「有没有东西可转写」唯一可靠、且不依赖上报链路的输入。
2. 停止判据改为 `shouldStopForSilence()`：**音频连续静音 ≥ 30 秒** 且 **位置冻结 ≥ 15 秒**，两者同时成立才停。位置冻结但音频有声 → 继续录；音频静音但位置在走 → 继续录（视频里可能本来就有无人声片段）。
3. `trackTimeline()` 提到 `updateSample()` 最前面，任何 early return 之前都先刷新推进时刻与锚点。
4. 测不到电平（AudioContext 被挂起/中断）时按「不知道」处理：刷新 `lastAudibleAt`，绝不在测不到的时候判静音。
5. 时间轴改为「锚点 + 墙钟」：位置上报断了也能按真实时长切分片，不再把整段压成 0 秒而被当成「过短」丢掉。

**影响范围**：`src/asr/tab-protocol.ts`、`src/asr/tab-recorder.ts`。协议与消息类型不变。

**验证**：`tsc` 0 错误；**29 文件 / 403 项全通过**（新增 4 项：位置冻结但音频有声不停止、音频静音但位置在走不停止、两者同时成立才停止、静音窗口必须长于停滞窗口）；构建版本 `0.12.4`。

## 16. 转写准确率：已支持与可选的改进方式

### 16.1 现状

- **页内字幕轨道**：已支持（`LIST_PAGE_TRACKS` / `READ_PAGE_TRACK`），B站与 YouTube 的 `<track>`、timedtext XML、json3 都能读。**但目前需要手动点「读取页内字幕」**，不会在「从音频转写」前自动优先尝试。
- **音频转写**：本机 Whisper（Whishper 容器，默认 `tiny`），不带术语表、不做上下文提示、不跨分片拼接上下文。
- **画面**：只用于手动「抓帧做笔记」，不参与文字生成。

### 16.2 可选的改进方式（按性价比排序）

- **A. 自动优先站方字幕**：点「从音频转写」时先列轨道并试读，有可用字幕就直接用，没有才录音。收益最高（官方/人工字幕最准，还省掉整段录音时间）。限制：站点没有字幕时仍走 ASR；部分站点字幕在 `blob:` 或需要登录才可读。
- **B. 换更大模型**：`tiny → small`（容器已加载 `small`）。中文识别明显更准。限制：CPU 上 `small` 实测约 0.73× 实时，会积压；`medium` 基本跟不上。
- **C. 术语表 / 上下文提示**：把视频标题、简介、人名术语作为 `initial_prompt` 传给 Whisper，分片带上一片末尾做上下文。专有名词、人名、型号错误显著减少；纯 CPU 下几乎零额外成本。需要你提供术语表。
- **D. 跨分片拼接**：分片边界前后各留 1–2 秒重叠，按时间轴去重。减少切分处断词、漏词；略微增加转写量。
- **E. 硬字幕 OCR**：定时抓帧 → OCR 识别烧进画面的字幕。无轨道、无音轨也能拿到原文。限制：需要 `tabCapture` 视频流或 `tabs.captureVisibleTab`；跨域媒体会污染 canvas 导致抓帧失败；Tesseract.js 中文包 10MB+，准确率与延迟都不如 ASR。
- **F. 画面辅助校对**：抽帧交给多模态模型，按画面里的板书/PPT/关键词纠正 ASR 错字。对专有名词、数字、公式最有效。限制：**图片会离开本机**，需要你同意并有可用多模态模型；按帧计费；只能在摘要/校对阶段做，不能实时。

推荐组合：**A（优先）→ C + D（低成本必做）→ B（够用即可）→ F（可选，需要你确认数据去向）**。E 只在「既没有轨道、音频又不可用」时才值得做。

### 16.3 需要你提供的信息

1. **具体页面**：出错的视频链接（或站点名 + 是否有原生 CC 字幕按钮）。决定 A 能否生效。
2. **是否有站方字幕**：播放器有没有「字幕/CC」开关，有的话是什么语言。
3. **错例对照**：任意 2–3 句「原话 → 被识别成什么」，用来判断是音频质量、模型词汇还是分片边界问题。
4. **术语表**：人名、产品名、型号、缩写（哪怕 10 个词），用于 `initial_prompt`。
5. **模型偏好**：能否接受 `small` 的 0.73× 实时（10 分钟视频约 13–14 分钟转完）；或是否愿意把容器 `CPU_THREADS` 从 4 提到 8–12（需重建容器；模型在容器层，重建会触发重新下载）。
6. **画面是否可上云**：若选 F，需要你确认「允许把抽帧图片发送到哪个多模态模型」，以及是否接受按帧计费。不同意则 F 不做，改用 C/D。
7. **是否直接实现 A**：这是唯一不需要额外信息、只改扩展内部顺序的改动（约 1 个函数 + 回归测试），确认后即可做。

## 18. 字幕与总结没有自动出现（0.12.6）

### 18.1 现象与判定

区分三种可能后，结论是「触发条件从来没被满足」，不是渲染问题：

- **输出渲染**：`TranscriptPanel` 仅在 `cues.length > 0` 时渲染，`SummaryPanel` 仅在 `state.summary` 存在时渲染 → 渲染逻辑正常，不是渲染缺陷。

### 18.2 根因

**① 字幕：推荐逻辑挂在按钮里，不是自动流程。**

- 打开弹窗但还没播到 30 秒 → 没有会话 → `snapshot()` 返回「请先获取、导入或转写字幕」且 `summary: null` → 面板空白；

## 22. 进度/音量滑块「拉不动」的真实原因（0.12.10）

### 22.1 受控输入 + 1.5 秒轮询 = 拖一下就弹回

**位置**：`src/ui/PlaybackBar.tsx`。

```tsx

onChange={(e) => onAction('seek', Number(e.target.value))} // 只发请求，不改本地
```

拖动时 `onChange` 只是把请求发给后台，props 里的 `state.positionMs` 还没变，

```tsx
const duration = state.durationMs > 0 ? state.durationMs : 1;  // 兜底成 1

```

## 30. 前几段有内容、后面的节点显示「没有可用字幕」（0.13.11）

### 30.1 现象与关键线索

结论：**字幕链路是通的**（否则节点 0 无法引用真实 cueId），问题在于

### 30.2 根因（边采边显示时的落库缺陷）

`src/ui/useStudyWorkflow.ts` 的音频采集轮询里，原逻辑是：

```ts
if (!liveTranscriptIdRef.current && view.status !== 'completed') { /* 落库一次 */ }
```

于是它永远只看到第一片（约 8 秒）的字幕：

```text

节点 4 (120–150s) → 库里没有这段字幕 → 判空、不请求模型
```

### 30.3 修复

1. `src/storage/db.ts` 新增 `replaceTranscriptCues(transcriptId, cues)`：
   在**同一版本 id 下**替换条目并更新 `cueCount`，不新建版本，
   避免会话与已完成节点因版本漂移而失联；版本不存在时明确失败，不写孤儿字幕。
2. `useStudyWorkflow` 的采集轮询改为：每片只要条数变化就同步进同一版本
   （`liveTranscriptIdRef` 复用、`liveCueCountRef` 跳过重复写入）；
   新一轮采集开始时重置这两个 ref。

## 31. 引用缺失 + 后台自动重试 + 整段总结（0.14.0）

### 31.1 「节点结论缺少原字幕引用」的成因

报错来自 `src/ai/auto-summary.ts` 的 `checkRefs`（`kind=missing-refs`）：
模型给某个 `paragraphs`/`bullets` 块漏写了 `sourceCueIds`，或把它写到了
`title` 层级以为能继承。校验器**不允许**补造或从上往下广播引用，所以整段作废。

### 31.2 三层处理

1. **提示词加固**（`buildAutoSummaryMessages`）：
   把可用 `cueId` 直接列进 system 提示，明确「`sourceCueIds` 是每个块的必填字段」
   「不要提到 `title` 层级」「不要写成单个字符串」。
2. **一次原地重写**（`runNode`）：仅当失败类型属于引用类
   （`missing-refs` / `unknown-refs` / `refs-type` / `refs-format`）且仍是第 0 轮时，
   带上失败原因与真实 `cueId` 列表重写一次。JSON 语法坏、正文空、结构缺失**不重写**。
   重写仍不合格就失败——绝不替模型补引用。
3. **后台自动重试失败段**（`retryFailedNodes`，由心跳 alarm 驱动）：
   无需弹窗开着；只重排「可恢复」失败（网络/超时/格式/校验），
   `AUTH_FAILED`/`QUOTA_EXCEEDED`/`PROVIDER_NOT_CONFIGURED`/`PERMISSION_DENIED`/
   `CONSENT_REQUIRED`/`NOT_FOUND` 一律跳过；`attempts >= MAX_AUTO_RETRY_ATTEMPTS(4)` 不再拾起。

### 31.3 新增：从字幕直接总结到笔记

入口在总结页：**「从字幕直接总结（全部 N 条）」**。

- `planFullSummary`：先显示「共 N 条字幕，分 M 段」，不发请求；
- `runFullSummary`：按完整 cue 边界分块（每块 ≤240 条 / ≤8000 字），逐块请求并校验，
  **有多少字幕就总结多少**；任一段失败则整体失败，不返回半份成稿；
- `appendSummaryToNote`：结果落到 `summaries` 并**追加**到笔记末尾，
  不动用户手写内容（原有文字保持在前）；
- 超过 `MAX_FULL_SUMMARY_CHUNKS(40)` 段时明确拒绝，而不是只总结一部分。

引用护栏完全相同：每段的引用只能来自该段真实 `cueId`，越界一律失败。

## 32. kind=syntax 的第三种成因：结构位非 ASCII 空白（0.14.1）

### 32.1 现象与定位

整段总结报：

```text
第 1/1 段未通过校验：模型正文中的 JSON 语法有误
phase=model-json; kind=syntax; chars=1925; candidates=1
```

`candidates=1` 表示只找到一个根对象（不是多结果歧义），`kind=syntax` 表示
解析器认定「它想写 JSON 但语法不合法」。

**用脚本实测**（不靠猜）：把 `JSON.parse` 直接喂给各类空白分隔的结构串，
结果全为失败——

| 字符 | 结果 |
| --- | --- |
| 全角空格 U+3000 | 失败 |
| 不换行空格 U+00A0 | 失败 |
| 零宽空格 U+200B | 失败 |
| 中间 BOM U+FEFF | 失败 |
| 窄空格 U+202F | 失败 |
| 普通半角空格 | 通过 |

原因是 **JSON 只认 空格 / `\t` / `\n` / `\r` 四种空白**。中文模型经常在
`"title"：` 后面顺手带上全角空格或零宽空格，于是整串 JSON 直接语法错误。

### 32.2 修复

`src/ai/json-output.ts` 的 `normalizeSyntax` 增加一条**仅作用于结构位**的规则：

```ts
const NON_JSON_SPACE = /[\u00a0\u1680\u2000-\u200b\u2028\u2029\u202f\u205f\u3000\ufeff]/;
```

- 结构位命中 → 替换为半角空格，并计入 `wideSpaces`；
- **字符串内部的同类字符是正文内容，一字不改**（走 `quoted` 分支，不经过该规则）；
- 为什么这一步「可证明不改值」：空白在 token 之间没有语义，替换只保留「分隔」作用。

> 关键坑：U+200B（零宽空格）与 U+FEFF（BOM）在 JS 正则里**不属于 `\s`**。
> 第一版用 `/\s/` 判定，结果这两个字符匹配不到、仍报 `kind=syntax`；
> 换成显式字符类后通过。日志新增 `wideSpaces` 计数字段，下次可直接确认。

## 33. 本地 Whisper「时间戳超出实际录音片段」（0.14.2）

### 33.1 根因

`src/asr/local-whisper.ts` 原来用 `durationMs` 硬卡时间戳：

```ts
if (start >= durationMs) throw ... '本地 Whisper 时间戳超出实际录音片段'
```

但 `durationMs` 是录音端的**墙钟估算**（`performance.now()` 差值，再与媒体推进取小），
而 Whisper 解析的是**真实音频流**：WebM/Opus 有容器预填充与编码缓冲，
音频实际长度会略大于墙钟估算。于是最后一句常出现 `start` 比 `durationMs`
大几十到几百毫秒——那是真实语音，却被判成越界，导致**整片丢失**。

### 33.2 修复（两道）

1. **录音端取真实时长**（`tab-recorder.ts`）：入队前用
   `AudioContext.decodeAudioData` 量出这一片的真实音频时长，作为 `durationMs`
   传给校验；解码失败才退回墙钟估算（返回 0，不伪造）。
2. **校验端留边界容差**（`normalizeLocalSegments`）：
   `limitMs = durationMs + EDGE_SLACK_MS(1500)`，超出部分夹到上限；
   起点超过 `limitMs` 仍整片失败。

护栏没有松动：30 秒片段给出 `start=40s` 这类**真错片**依旧拒绝；
倒序、负值、非数字、空文本、有文本无分段的判定完全不变。

## 34. 弹窗关闭时也静默取字幕（0.15.0）

### 34.1 为什么需要

用户目标：**播到一半再打开弹窗，直接看到已经累积的自动学习内容**。

旧实现里取字幕只发生在弹窗组件内（`useStudyWorkflow` 的两个 effect），于是
关闭弹窗期间不读字幕 → 自动学习会话不存在 → 那段时间的学习**永久缺失**。

### 34.2 现在的触发链路

`VIDEO_CONTEXT_CHANGED`（页面内容脚本上报视频身份）→ 后台 `rememberContext` 之后
追加 `silentBootstrap({ tabId, videoId, platform, aid, cid })`：

1. 若该视频已有字幕版本 → 直接沿用，不再发起网络请求；
2. 否则先读页内 `<track>` / 站点脚本字幕（按 `rankCaptionTracks`，人工/官方优先）；
3. 再试 B 站站方字幕（需 `aid`/`cid`，带 `credentials: 'include'`）；
4. 拿到即 `saveTranscript` 落库，随后 `prepare(videoId, transcriptId)` 建立自动学习会话
   （**只建会话，不请求模型**），后续随播放的 30 秒节点就能正常累积。

同一 `videoId` 在一次页面寿命内只尝试一次（`attempted` 集合），避免位置上报反复触发。

### 34.3 明确不做的两件事

- **不自动录音转写**：`tabCapture.getMediaStreamId` 需要用户手势，后台无法发起；
  且转写要求视频以 1 倍速**出声**播放整段时长，静默启动既不可行也会打扰用户。
  取不到字幕时只记录原因（`no-track` / `unreadable` / `failed`），等用户决定。
- **不绕过权限与登录**：读不到就如实记录，不伪造字幕。

### 34.4 弹窗内仍有兜底

弹窗的自动取字幕 effect 保留：后台静默失败（例如页面脚本尚未注入）时，
打开弹窗仍会再试一次，并给出「可点从音频转写 / 导入文件」的明确引导。
